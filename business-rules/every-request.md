# Rules for every request

- **loud**, auth/-: A request is sent from the merchant's backend server (the definition expects every request to come from one) → outcome not stated. **Do:** Send `Authorization: Bearer {secret}.{jwt}` (the application token's secret, a dot, then the token) on every server-side request. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/general/authentication.md`; `every-request.1`)*
- **loud**, auth/errors: A request authenticated with a store application token without its secret (`Bearer {jwt}`, as the widget and inline form send it) comes from an `Origin` domain that is not registered on that application token → 401 "INVALID_DOMAIN" Tested without the secret: GET /stores/{storeId}/tokens?type=recurring returned 401 INVALID_DOMAIN and GET /me returned 401 with an empty body; GET /checkout_info sent from a server, or with a Referer and no Origin, returned 401 INVALID_DOMAIN, and with Origin https://example.com, http://localhost or http://localhost:8081 returned 403 with an empty body, also when the token's domains listed localhost. **Do:** Register every domain that hosts the widget or inline form on the store application token, never send the secret from a browser, and treat a 401 or 403 with an empty body as the same refusal. **Conflict:** The definition and the error table say a request from an Origin not registered on the token gets 401 INVALID_DOMAIN; on GET /checkout_info the tested page saw 403 with an empty body for the Origins it tried, even one registered on the token, and 200 from UnivaPay's widget and checkout hosts; the record follows the tested page for the cases it tested and the definition elsewhere. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/general/authentication.md`; docs `content/ja/docs/api/error/overview.md`; docs `content/tested/sandbox-api-behaviour.md`; `every-request.2`)*
- **loud**, auth/errors: A request has no `Authorization` header → 401 "AUTH_HEADER_MISSING". **Do:** Always send the `Authorization` header; treat 401 AUTH_HEADER_MISSING as a bug in the client, not as a payment result. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; `every-request.3`)*
- **loud**, auth/errors: The application token in the `Authorization` header is not valid → 401 "INVALID_APP_TOKEN". **Do:** Check that the header carries a current application token of the right store and mode before retrying. *(spec `spec/openapi.yaml`; `every-request.4`)*
- **loud**, auth/errors: The credentials sent (application token and secret) are not correct → 401 "INVALID_CREDENTIALS". **Do:** Send the secret that belongs to the same application token; a lost secret means creating a new application token. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/general/authentication.md`; `every-request.5`)*
- **loud**, auth/errors: The application token was issued in an old version format → 403 "OUTDATED_APP_TOKEN". **Do:** Create a new application token in the console and replace the old one. *(spec `spec/openapi.yaml`; `every-request.6`)*
- **loud**, auth/errors: The application token is the wrong type for the request, or the account lacks the permission → 403 "INVALID_PERMISSIONS". **Do:** Use a store application token (with its secret) for store requests, and ask support when the account lacks a permission. *(spec `spec/openapi.yaml`; `every-request.7`)*
- **loud**, other/errors: The API is called from a browser through a cross-origin (CORS) request → outcome not stated. **Do:** Call the API from the merchant's server application, never directly from browser code. *(docs `content/ja/docs/api/general/api_cooperation.md`; `every-request.8`)*
- **loud**, other/errors: In test mode, a request with a store application token is sent to `https://api.gyro-n.money` instead of `https://api.univapay.com` (tested on GET /me) → 401. **Do:** Send every request (except direct debit) to `https://api.univapay.com`. *(docs `content/tested/sandbox-api-behaviour.md`; spec `spec/openapi.yaml`; `every-request.9`)*
- **loud**, -/errors: A request fails as an API request error → outcome not stated. **Do:** Branch on the HTTP status (4xx or 5xx) and on the JSON body's `code` (UPPER_SNAKE_CASE); read `errors[].field` and `errors[].reason` for details, and accept that some errors come with no JSON body. *(docs `content/ja/docs/api/general/response.md`; docs `content/ja/docs/api/error/overview.md`; `every-request.10`)*
- **loud**, -/errors: A request parameter fails validation → 400 "VALIDATION_ERROR". **Do:** Read each `errors[].field` and `errors[].reason` to find the bad parameter and fix the request instead of retrying it unchanged. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; `every-request.11`)*
- **loud**, -/errors: The path, or a resource id in it (such as a store id or token id), does not exist → 404. **Do:** Check the ids in the path (and that they belong to the token's store and mode) before retrying. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; `every-request.12`)*
- **loud**, resilience/errors: An unexpected internal error occurs while the request is processed → 500. **Do:** Do not assume nothing happened: fetch the resource (or list it) to see what was done before retrying, and send writes with an `Idempotency-Key`. *(docs `content/ja/docs/api/error/overview.md`; `every-request.13`)*
- **loud**, resilience/errors: The service is temporarily unavailable → 503 "SERVICE_UNAVAILABLE_TRY_AGAIN". **Do:** Wait and retry the request later. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; `every-request.14`)*
- **loud**, other/errors: The connected gateway system does not support the request → 504 "NO_GATEWAY_AVAILABLE_TO_PROCESS_THE_REQUEST". **Do:** Do not retry unchanged; contact UnivaPay support. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; `every-request.15`)*
- **loud**, limits/errors: A client exhausts a burst rate on a request other than POST /tokens, POST /charges and POST /subscriptions (those count against the charge rate limit instead): these requests count against the route burst rate (limit 30, 1,200 per minute per path) and the exact burst rate (limit 10, 120 per minute per exact path including ids and query string) → 429. **Do:** Watch the `X-Remaining-Requests-*` response headers, slow down before they reach 0, and on 429 wait for the burst rate to refill before retrying. *(docs `content/ja/docs/api/general/api_limit.md`; docs `content/ja/docs/api/error/overview.md`; docs `content/ja/docs/faq/individual/api.md`; `every-request.16`)*
- **loud**, limits/errors: A request is refused with 429 Too Many Requests; the docs show this response with no body (`Content-Length: 0`), while the definition says it returns an empty JSON object → 429. **Do:** Handle 429 from the status code alone; do not expect an error `code` in the body. **Conflict:** The error-code page shows a 429 with no body; the definition says an empty JSON object; not tested. The record says the sources disagree. *(docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; `every-request.18`)*
- **loud**, idempotency/errors: An `Idempotency-Key` that was already used on a different API or method is sent (tested on PATCH /stores/{storeId}/charges/{id}: also when it was used on a different charge) → 409 "IDEMPOTENCY_KEY_CONFLICT" The response header `Idempotency-Status` is `conflicting_key`. **Do:** Generate a fresh `Idempotency-Key` for each distinct request and resource; on 409 IDEMPOTENCY_KEY_CONFLICT, resend with a new key only after checking the first request's effect. *(docs `content/ja/docs/api/general/idempotent-requests.md`; docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; docs `content/tested/sandbox-api-behaviour.md`; `every-request.23`)*
- **loud**, idempotency/errors: The cache entry for the `Idempotency-Key` is found but the earlier result cannot be read → 500 "UNABLE_TO_GET_IDEMPOTENT_RESULT". **Do:** Do not resend with a new key; fetch the resource to learn the first request's result. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; `every-request.25`)*
- **loud**, limits/-: The whole request body is larger than 256KB (metadata has no limit on the number of keys, but counts toward this) → outcome not stated. **Do:** Keep each request body, including metadata, under 256KB. *(docs `content/ja/docs/api/general/metadata.md`; `every-request.29`)*
- **loud**, account-config/errors: Live mode is used before the account's review is complete → 400 "LIVE_MODE_NOT_ENABLED_WHEN_UNVERIFIED". **Do:** Use test mode until UnivaPay has finished reviewing the account. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; `every-request.32`)*
- **silent**, limits/values: Any request is answered → The response headers carry the remaining burst rate and the per-minute limit (`X-Remaining-Requests-Exact`, `X-Remaining-Requests-Route`, `X-Requests-Per-Minute-Exact`, `X-Requests-Per-Minute-Route`; on the charge-rate calls `X-Remaining-Requests` and `X-Requests-Per-Minute`). **Do:** Read these headers to pace requests instead of waiting for a 429. *(docs `content/ja/docs/api/general/api_limit.md`; `every-request.17`)*
- **silent**, idempotency/other: An `Idempotency-Key` header is sent on a request that is not POST or PATCH, or on an operation that does not support idempotent requests → Idempotent handling is only available for POST and PATCH requests; where idempotent requests are not supported, the response header `Idempotency-Status` is `disabled`. **Do:** Send `Idempotency-Key` (a random UUID) on every POST and PATCH that creates or changes tokens, charges, subscriptions or refunds, and treat `Idempotency-Status: disabled` as no protection against duplicates. *(docs `content/ja/docs/api/general/idempotent-requests.md`; spec `spec/openapi.yaml`; `every-request.19`)*
- **silent**, idempotency/other: A POST or PATCH request carries an `Idempotency-Key` that has not been used before (tested on PATCH /stores/{storeId}/charges/{id}) → The request is processed normally, its response is stored under the key, and the response header `Idempotency-Status` is `successfully_stored`. **Do:** Keep the key with the pending operation so a retry after a timeout reuses the same key. *(docs `content/ja/docs/api/general/idempotent-requests.md`; docs `content/tested/sandbox-api-behaviour.md`; `every-request.20`)*
- **silent**, idempotency/other: A POST or PATCH request repeats an `Idempotency-Key` used within the last 24 hours on the same resource, also with a different body (tested on PATCH /stores/{storeId}/charges/{id}, POST /charges and POST refunds; capture and cancel do not apply the key) → The request is not processed again; the stored response is returned with `Idempotency-Status: retrieved_idempotent_response`. **Do:** Retry a timed-out write with the same `Idempotency-Key`, and read `Idempotency-Status` to tell a replay from a new result. *(docs `content/ja/docs/api/general/idempotent-requests.md`; docs `content/tested/sandbox-api-behaviour.md`; `every-request.21`)*
- **silent**, idempotency/other: An `Idempotency-Key` is sent again more than 24 hours after its first use → The key has expired: the API treats the request as a first request and executes it again. **Do:** Do not rely on a key older than 24 hours to block a duplicate; check the resource's state before retrying an old write. *(docs `content/ja/docs/api/general/idempotent-requests.md`; `every-request.22`)*
- **silent**, idempotency/other: The idempotency check cannot be made (it is best effort) because reading or writing the key cache fails → The request is still processed, and the response header `Idempotency-Status` is `error`. **Do:** When `Idempotency-Status` is `error`, treat the request as not protected against duplicates and check for duplicates before retrying. *(docs `content/ja/docs/api/general/idempotent-requests.md`; `every-request.24`)*
- **silent**, -/lists: A list endpoint is called without paging parameters → Items come newest first (descending creation date), 10 per page, with `has_more` telling whether more items follow. **Do:** Page through lists until `has_more` is false instead of assuming one response holds everything. *(docs `content/ja/docs/api/general/pagination.md`; `every-request.26`)*
- **silent**, -/lists: A list endpoint is called with `cursor` set to a resource id → The page starts with the resource right after that id; the cursor resource itself is not included. **Do:** Pass the last item's `id` from the previous page as `cursor` to get the next page. *(docs `content/ja/docs/api/general/pagination.md`; spec `spec/openapi.yaml`; `every-request.27`)*
- **silent**, limits/lists: A list endpoint is called with a `limit` outside 10 to 100 (the docs and the definition say 10 to 100; tested on the charge list with limit=5 and limit=101) → 200 Accepted in test mode: limit=5 returned 5 items with has_more true, and limit=101 also returned 200. **Do:** Keep `limit` between 10 and 100 yourself; the API did not refuse 5 or 101 on the charge list in test mode. **Conflict:** content/ja/docs/api/general/pagination.md and spec/openapi.yaml say limit must be 10 to 100, but the tested page saw 5 and 101 accepted on the charge list; the record follows the tested page. *(docs `content/ja/docs/api/general/pagination.md`; spec `spec/openapi.yaml`; docs `content/tested/sandbox-api-behaviour.md`; `every-request.28`)*
- **silent**, -/values: An amount is sent in a currency with a minor unit (e.g. USD cents) → The amount is read as one integer in the smallest currency unit (10.00 USD is 1000). **Do:** Convert amounts to an integer of the smallest unit before sending, and convert back when reading. *(docs `content/ja/docs/api/general/currency-exchange.md`; `every-request.30`)*
- **silent**, account-config/values: A request is made with a test-mode application token → The request is processed in test mode; live payments need a live-mode application token. **Do:** Use a test-mode application token for testing and switch to a live-mode application token to take real payments. *(docs `content/ja/docs/faq/individual/test.md`; `every-request.31`)*
