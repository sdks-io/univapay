# Refunds

## `GET /stores/{storeId}/charges/{chargeId}/refunds` (`listRefunds`)

- **silent**, -/lists: The refunds of a charge are listed a few seconds after a refund was created → The new refund may not be in the list yet (the list is not strictly real-time). **Do:** Use GET refund by id, not the list, to read a refund just created. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/refunds/request/list.md`; `listRefunds.1`)*

## `POST /stores/{storeId}/charges/{chargeId}/refunds` (`createRefund`)

- **loud**, limits/-: `security_configuration.refund_percent_limit` is set and the refund would take total refunds above that share of the merchant's total charges → outcome not stated. **Do:** Check refund_percent_limit before large or repeated refunds. *(docs `content/ja/docs/api/merchant/overview.md`; spec `spec/openapi.yaml`; `createRefund.1`)*
- **loud**, other/errors: The charge to refund is a bank-transfer charge that is successful (paid); an awaiting one is refused with CANNOT_REFUND_UNSUCCESSFUL_CHARGE instead → 400 "REFUND_NOT_ALLOWED". **Do:** Refund bank-transfer payments directly to the customer's bank account outside UnivaPay. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/faq/individual/bank.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/guide/individual/bank/feature.md`; docs `content/ja/faqsite/article-000001041.md`; `createRefund.2`)*
- **loud**, state/-: A partial refund is requested for a charge paid with MCP (Multi-Currency Pricing, the customer paying in another currency in the widget or link form) → outcome not stated. **Do:** Refund MCP charges only in full; do not attempt a partial refund. *(docs `content/ja/docs/guide/detail/mcp.md`; `createRefund.4`)*
- **loud**, state/errors: A refund is created for a charge that is not successful (tested: an awaiting konbini charge, an awaiting bank-transfer charge, and an authorized card charge) → 400 "CANNOT_REFUND_UNSUCCESSFUL_CHARGE". **Do:** Refund only successful charges; for an awaiting or authorized charge, check the charge and use a cancel where its payment method allows it. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/cancels/overview.md`; `createRefund.6`)*
- **loud**, other/errors: A refund is created for a successful konbini charge → 400 "REFUND_NOT_ALLOWED". **Do:** Return konbini payments to the consumer outside UnivaPay. *(docs `content/tested/sandbox-api-behaviour.md`; spec `spec/openapi.yaml`; docs `content/ja/faqsite/article-000001041.md`; `createRefund.8`)*
- **loud**, account-config/errors: A refund is created while refunds are not allowed for the merchant or store (refund permission is set per platform), or the refund is otherwise refused → 400 "REFUND_NOT_ALLOWED". **Do:** Check with UnivaPay that refunds are enabled for the merchant and store. *(docs `content/ja/docs/api/error/overview.md`; docs `content/ja/docs/faq/individual/test.md`; announcement `content/ja/docs/changelog/2023-2.md`; `createRefund.9`)*
- **loud**, limits/errors: A single refund amount is larger than the charge amount → 400 "VALIDATION_ERROR". **Do:** Refund at most the charged amount; read errors[].reason REFUND_NOT_WITHIN_BOUNDS on the amount field. **Conflict:** The error table and the FAQ site list REFUND_NOT_WITHIN_BOUNDS as a top-level error code; the tested page shows it as errors[].reason under VALIDATION_ERROR; the record follows the tested page. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/error/overview.md`; docs `content/ja/faqsite/article-000001041.md`; `createRefund.10`)*
- **loud**, state/errors: A refund, added to the earlier refunds of the charge, would exceed the charge amount (including a new refund on a fully refunded charge) → 400 "REFUND_EXCEEDS_CHARGE_AMOUNT". **Do:** Track the refunded total per charge and refund only the remaining amount. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/error/overview.md`; docs `content/ja/docs/api/refunds/overview.md`; `createRefund.11`)*
- **loud**, other/errors: A refund is made in a currency other than the charge's currency → 400 "VALIDATION_ERROR". **Do:** Refund in the charge's charged_currency (not requested_currency when the charge was converted). **Conflict:** The error table lists CURRENCY_MUST_MATCH_CHARGE as a top-level error code; the tested page shows it as errors[].reason under VALIDATION_ERROR; the record follows the tested page. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/refunds/overview.md`; `createRefund.12`)*
- **loud**, account-config/-: Outside test mode, a partial refund is requested for a card, PayPay online or other method: the refund FAQ says only Alipay, WeChat, Paidy and d-barai Online support partial refunds and the FAQ site says card and PayPay online do not, but the definition says most methods support them (sources disagree) → outcome not stated. **Do:** Expect partial refunds of card and PayPay online charges to be refused or to fail (payment error 318), and handle a full refund plus a new charge as the fallback. **Conflict:** The refund FAQ and FAQ site say card and PayPay online refunds are full only; the definition says most methods support partial refunds; the tested page saw partial card and PayPay online refunds succeed only in test mode; the sources disagree for live mode. *(docs `content/ja/docs/faq/individual/refund.md`; docs `content/ja/faqsite/article-000001065.md`; docs `content/ja/faqsite/article-000001041.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/error/overview.md`; docs `content/tested/sandbox-api-behaviour.md`; `createRefund.14`)*
- **loud**, limits/errors: A refund is larger than the current month's net sales (charges minus refunds of the month), for example refunding last month's charge early in the month → 400 "REFUND_EXCEEDS_SALES". **Do:** Wait until the month's sales cover the refund, or return the money to the consumer directly. *(docs `content/ja/docs/api/error/overview.md`; docs `content/ja/docs/guide/first/restriction.md`; spec `spec/openapi.yaml`; docs `content/ja/faqsite/article-000001041.md`; docs `content/ja/faqsite/article-000001053.md`; `createRefund.15`)*
- **loud**, state/-: In test mode, a charge whose recurring token was deleted automatically after 180 days is refunded → outcome not stated. **Do:** Do not expect to refund test charges older than 180 days. *(docs `content/ja/docs/faq/individual/test.md`; `createRefund.19`)*
- **loud**, state/errors: A refund reason is set to a value that is not allowed: chargeback_reverse at creation, or a change between a chargeback reason and a non-chargeback reason (chargeback is set only by the system) → 400 "INVALID_REFUND_REASON". **Do:** Set only fraud, duplicate or customer_request as the refund reason, and never change a chargeback reason. Also: `updateRefund`. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/refunds/overview.md`; `updateRefund.1`)*
- **silent**, account-config/side-effects: A payment succeeds, an authorization is captured, or a refund is made, and the matching email notification is enabled → UnivaPay emails the payment-completion notice to the email address used for the payment (the merchant's template, or the default one if none was made). **Do:** Do not send a duplicate email for this event unless the matching notification is switched off in the console (General settings > Notifications). Also: `createCharge`, `captureCharge`. *(docs `content/ja/docs/guide/detail/mail/template.md`; docs `content/ja/docs/guide/detail/mail.md`; docs `content/ja/docs/faq/individual/mail.md`; `createCharge.15`)*
- **silent**, other/side-effects: A pre-processing error occurs before the payment request is executed, for example because of wrong input → The charge or refund is accepted but ends failed with payment error 500 in error.code (a payment-error code, not an HTTP status). **Do:** On payment error 500, check the request input against the error message and correct it before trying again. Also: `createCharge`. *(docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; `createCharge.92`)*
- **silent**, other/side-effects: An internal error occurs while the payment is processed → The charge or refund is accepted but ends failed with payment error 501 in error.code (a payment-error code, not an HTTP status). **Do:** On payment error 501, contact UnivaPay support. Also: `createCharge`. *(docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; `createCharge.93`)*
- **silent**, resilience/side-effects: The payment request times out while waiting for a response → The charge or refund is accepted but ends failed with payment error 502 in error.code (a payment-error code, not an HTTP status). **Do:** On payment error 502, wait a while and then try the payment again. Also: `createCharge`. *(docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; `createCharge.94`)*
- **silent**, other/side-effects: The connected payment system does not support the request → The charge or refund is accepted but ends failed with payment error 504 in error.code (a payment-error code, not an HTTP status). **Do:** On payment error 504, contact UnivaPay support instead of retrying the same request. Also: `createCharge`. *(docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; `createCharge.95`)*
- **silent**, idempotency/other: A POST /charges or refund request carrying an Idempotency-Key is refused with an error (tested with 400 errors, and with a 404 for an unknown transaction_token_id) → The reply has Idempotency-Status not_stored: the refusal is not stored under the key, and on POST /charges the same key sent with a corrected body created the charge. **Do:** After a refusal, fix the request and resend it; the same key may be reused because the refusal was not stored. Also: `createCharge`. *(docs `content/tested/sandbox-api-behaviour.md`; `createCharge.97`)*
- **silent**, state/values: A refund or a cancel is requested → Its status changes in stages: `pending`, then `successful`, `failed` or `error`. **Do:** Do not treat the create response as the result; poll the refund or cancel (or wait for its webhook) until it is final. Also: `createCancel`. *(docs `content/ja/docs/guide/first/notification_and_retrieval.md`; docs `content/ja/docs/api/refunds/overview.md`; spec `spec/openapi.yaml`; `createRefund.3`)*
- **silent**, -/values: An MCP charge is refunded → The refund amount is calculated with the conversion rate fixed at the time of payment. **Do:** Show the customer the refund in the currency and rate of the original payment, not today's rate. *(docs `content/ja/docs/guide/detail/mcp.md`; `createRefund.5`)*
- **silent**, state/side-effects: In test mode, a partial refund of a successful card charge (tested: 1,000 of 10,000 JPY, then further partial refunds) or PayPay online charge (tested: 400 of 1,000 JPY) is created → 201 The refund becomes successful (card: pending first, within seconds); further partial card refunds are accepted while the total stays within the charge amount. **Do:** Allow partial refunds of card and PayPay online charges in test mode, keeping the total within the charge amount. **Conflict:** The refund FAQ says only Alipay, WeChat, Paidy and d-barai Online support partial refunds, and the FAQ site lists card and PayPay online as full refund only; the tested page saw partial refunds of both succeed in test mode; the record follows the tested page for test mode. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/faq/individual/refund.md`; docs `content/ja/faqsite/article-000001065.md`; `createRefund.13`)*
- **silent**, -/webhooks: A refund reaches its final status → The refund_finished webhook is sent. **Do:** Subscribe to refund_finished to learn the refund result. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/refunds/overview.md`; `createRefund.17`)*
- **silent**, -/values: In test mode, a charge made with test card 4242 4242 4242 4242 is refunded → 201 The refund starts as pending and then becomes failed with error code 309, message Test refund failed purposely. **Do:** Use the 4242 test card to exercise failed refunds, and 4000020000000000 for successful ones. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/charges/overview.md`; docs `content/ja/docs/guide/first/verification.md`; `createRefund.18`)*
- **silent**, limits/values: A refund is requested after the payment method's refund period: about 180 days for card, 1 year for Alipay, 180 days for WeChat, 1 year for PayPay online, 1 year for Paidy, 180 days for d-barai Online → The refund ends in error. **Do:** Refund within the payment method's refund period; otherwise return the money outside UnivaPay. *(docs `content/ja/docs/faq/individual/refund.md`; `createRefund.20`)*
- **silent**, -/values: A card refund is made through an overseas acquirer → The refund can stay pending for 1 to 2 weeks before it becomes successful or failed. **Do:** Keep polling (or wait for refund_finished) for up to two weeks on overseas card refunds. *(docs `content/ja/docs/faq/individual/refund.md`; `createRefund.21`)*
- **silent**, -/values: A charge is refunded → The transaction fee of the refunded charge is still billed. **Do:** Do not expect the charge fee to be returned when refunding. *(docs `content/ja/docs/api/refunds/overview.md`; `createRefund.22`)*
- **silent**, idempotency/values: A refund is sent again with the same Idempotency-Key after the first refund has settled (tested) → 201 Idempotency-Status is retrieved_idempotent_response, the same refund id is returned, and the body is the first stored reply with status pending, not the current status. **Do:** Read a refund's current status with GET on the refund, not from a replayed create response. *(docs `content/tested/sandbox-api-behaviour.md`; `createRefund.23`)*

## `GET /stores/{storeId}/charges/{chargeId}/refunds/{id}` (`getRefund`)

- **loud**, resilience/errors: A GET of a payment resource returns 502, 503 or 504 (possibly a temporary network problem) → outcome not stated. **Do:** Retry the GET after a few seconds and do not treat these statuses as a failed payment. Also: `getCharge`, `getCancel`, `getSubscription`. *(docs `content/ja/docs/api/general/polling.md`; `getCharge.3`)*
- **silent**, -/values: A charge, refund, cancel or subscription is fetched with `polling=true` → The API polls internally and answers as soon as the resource reaches a final status (charge: canceled, error, failed, successful; refund and cancel: error, failed, successful), or after 3 seconds with whatever status it has then. **Do:** Use `polling=true` instead of a tight client-side loop, and repeat the call if the status is still not final after it returns. Also: `getCharge`, `getCancel`, `getSubscription`. *(docs `content/ja/docs/api/general/polling.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/charges/overview.md`; `getCharge.1`)*
- **silent**, -/values: A refund is fetched with polling=true while it is pending → The server holds the request until the refund reaches successful, failed or error, or the polling timeout (3 seconds) passes. **Do:** Repeat GET with polling=true until the refund is final. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/refunds/request/get.md`; docs `content/ja/docs/api/general/polling.md`; `getRefund.1`)*
