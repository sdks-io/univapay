# Checkout

## `GET /checkout_info` (`getCheckoutInfo`)

- **loud**, auth/errors: UnivaPay's checkout widget (or inline form) runs on a page whose host is not in the `domains` list of the app token it is given (the list is in the token's JWT payload) → The widget shows "Cannot run checkout from this domain." instead of the payment form (tested with a token whose domains were empty, on localhost); with the host listed, it opened. **Do:** Register every host the checkout runs on as a domain of the store app token used in the browser, and check the token's domains at startup. Also: `createTransactionToken`. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/general/authentication.md`; `createTransactionToken.51`)*
- **loud**, auth/errors: GET /checkout_info is called from a server with the app token alone (`Bearer {jwt}`, no secret) → 401 "INVALID_DOMAIN". **Do:** Call GET /checkout_info from the server with `Bearer {secret}.{jwt}`; a call with the app token alone is meant for the browser widget and was refused from a server. **Conflict:** The definition and the checkout-info pages say the app token alone is accepted; the tested page shows a server call with the app token alone gets 401 INVALID_DOMAIN (and 200 with the secret). The record follows the tested page. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/checkoutinfo/request/get.md`; docs `content/ja/docs/api/checkoutinfo/overview.md`; docs `content/tested/sandbox-api-behaviour.md`; `getCheckoutInfo.1`)*
- **loud**, auth/errors: GET /checkout_info is called with the app token alone (`Bearer {jwt}`) and the Origin https://example.com, http://localhost or http://localhost:8081 (tested; also when the token's domains list localhost) → 403 Empty body; with Origin https://widget.univapay.com or https://checkout.univapay.com the same call returns 200. **Do:** Do not call GET /checkout_info with the app token alone from your own pages; call it from your server with `Bearer {secret}.{jwt}`, and handle a 403 with an empty body as a refusal. **Conflict:** The definition says an Origin not registered on the token gets 401 INVALID_DOMAIN; the tested page saw 403 with an empty body, also for a domain listed on the token; the record follows the tested page. *(docs `content/tested/sandbox-api-behaviour.md`; spec `spec/openapi.yaml`; `getCheckoutInfo.5`)*
- **silent**, auth/values: Reading `mode` in the checkout info → `live` or `test` reflects the mode of the app token used for the call. **Do:** Use a live-mode app token when you need the live checkout settings. *(spec `spec/openapi.yaml`; docs `content/tested/sandbox-api-behaviour.md`; `getCheckoutInfo.2`)*
- **silent**, -/values: The store has not customised its widget theme colours; the definition says each colour resolves to the platform default shown in its examples (e.g. main_background #FFFFFF), but the checkout-info overview page lists other defaults (e.g. main_background #fafafa) → Each theme colour is returned with a default value and is never null. **Do:** Use the colour values returned instead of hard-coded defaults, since the sources disagree on the defaults. **Conflict:** The definition (CheckoutThemeColors) and content/ja/docs/api/checkoutinfo/overview.md give different default colours; not tested, so the record states both. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/checkoutinfo/overview.md`; `getCheckoutInfo.3`)*
- **silent**, account-config/values: The store has no recurring-charge CVV confirmation setting → `recurring_card_charge_cvv_confirmation.enabled` is returned as false. **Do:** Treat enabled false as no CVV re-confirmation for recurring card charges. *(spec `spec/openapi.yaml`; `getCheckoutInfo.4`)*
