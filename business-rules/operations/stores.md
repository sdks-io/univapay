# Stores

## `GET /stores` (`listStores`)

- **loud**, auth/-: The request is sent with the app token alone, without its secret (the docs list the secret as required for these calls); tested on GET /me only → 401 Empty body (tested on GET /me). **Do:** Send these calls from your server with `Authorization: Bearer {secret}.{jwt}`, never with the bare app token. Also: `getCurrentMerchant`, `getStore`, `createCustomerId`, `listTransactionHistory`, `listStoreTransactionHistory`, `listWebhooks`, `createWebhook`, `getWebhook`, `updateWebhook`, `createDirectDebitBankAccount`, `updateDirectDebitBankAccount`. *(docs `content/ja/docs/api/merchant/request/get.md`; docs `content/ja/docs/api/store/request/get.md`; docs `content/ja/docs/api/store/request/list.md`; docs `content/ja/docs/api/store/request/customer-uuid.md`; docs `content/ja/docs/api/transactions/request/list.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/webhooks/request/get.md`; docs `content/ja/docs/api/webhooks/request/update.md`; docs `content/ja/docs/api/bank-accounts/request/create.md`; docs `content/ja/docs/api/bank-accounts/request/update.md`; docs `content/tested/sandbox-api-behaviour.md`; `getCurrentMerchant.1`)*
- **silent**, -/lists: Filtering the store list with `search`: the store's name in upper case returns that store (tested); the docs page's intro also says a store ID can be given (untested) → 200 The store name is matched without regard to case. **Do:** Use `search` as a case-insensitive store-name filter, and fetch a known store with GET /stores/{id} instead of searching by its ID. **Conflict:** The definition (case-insensitive free text), the parameter table of content/ja/docs/api/store/request/list.md (store name) and its intro (store ID) differ; the tested page confirms a case-insensitive name match, which the record follows; matching by store ID is untested. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/store/request/list.md`; docs `content/tested/sandbox-api-behaviour.md`; `listStores.1`)*
- **silent**, other/lists: Reading a resource's current state from a LIST response → The list is not strictly real-time and may lag slightly behind the actual data. **Do:** Confirm the latest state of a single resource with its GET call, not with the list. Also: `listTransactionHistory`, `listStoreTransactionHistory`. *(docs `content/ja/docs/api/store/request/list.md`; docs `content/ja/docs/api/transactions/request/list.md`; `listStores.2`)*
- **silent**, auth/lists: Listing stores → Only the stores visible to the current merchant credentials are returned. **Do:** Expect the list to hold only the stores your credentials can access. *(spec `spec/openapi.yaml`; `listStores.3`)*

- **loud**, auth/-: The request is sent with the app token alone, without its secret (the docs list the secret as required for these calls); tested on GET /me only → 401 Empty body (tested on GET /me). **Do:** Send these calls from your server with `Authorization: Bearer {secret}.{jwt}`, never with the bare app token. - **silent**, -/values: Reading `configuration.percent_fee` or `configuration.flat_fees` of a merchant or store → The fee values may not exactly reflect the amounts actually used in settlement. **Do:** Do not compute settlement or payout amounts from these fee fields. Also: `getCurrentMerchant`. *(docs `content/ja/docs/api/merchant/overview.md`; docs `content/ja/docs/api/store/overview.md`; `getCurrentMerchant.4`)*
- **silent**, account-config/values: A merchant or store setting such as flat_fees, min_transfer_payout, limit_charge_by_card_configuration or a minimum charge amount is not set → The field is returned as null (GET /stores/{id} also returns minimum_charge_amounts and maximum_charge_amounts as null). **Do:** Parse these setting fields as nullable and treat null as not set. Also: `getCurrentMerchant`. *(docs `content/tested/sandbox-api-behaviour.md`; `getCurrentMerchant.5`)*
- **silent**, -/values: Reading a store's `configuration` from GET /stores/{id} → `transfer_schedule` is left out of the store configuration. **Do:** Read the payout schedule from GET /me, not from the store. *(spec `spec/openapi.yaml`; `getStore.1`)*

- **loud**, auth/-: The request is sent with the app token alone, without its secret (the docs list the secret as required for these calls); tested on GET /me only → 401 Empty body (tested on GET /me). **Do:** Send these calls from your server with `Authorization: Bearer {secret}.{jwt}`, never with the bare app token. Also: `getCurrentMerchant`, `getStore`, `listStores`, `listTransactionHistory`, `listStoreTransactionHistory`, `listWebhooks`, `createWebhook`, `getWebhook`, `updateWebhook`, `createDirectDebitBankAccount`, `updateDirectDebitBankAccount`. *(docs `content/ja/docs/api/merchant/request/get.md`; docs `content/ja/docs/api/store/request/get.md`; docs `content/ja/docs/api/store/request/list.md`; docs `content/ja/docs/api/store/request/customer-uuid.md`; docs `content/ja/docs/api/transactions/request/list.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/webhooks/request/get.md`; docs `content/ja/docs/api/webhooks/request/update.md`; docs `content/ja/docs/api/bank-accounts/request/create.md`; docs `content/ja/docs/api/bank-accounts/request/update.md`; docs `content/tested/sandbox-api-behaviour.md`; `getCurrentMerchant.1`)*
- **silent**, idempotency/values: createCustomerId is called again with the same `customer_id` for the same store → The same UUID is returned every time; nothing is stored, so repeats are safe and need no Idempotency-Key. **Do:** Derive the UUID again whenever you need it, without an Idempotency-Key, instead of treating each call as creating something. *(spec `spec/openapi.yaml`; `createCustomerId.1`)*
- **silent**, -/values: Deriving a customer UUID from the merchant's own customer_id → The UUID is derived per store (store-scoped), with the local customer_id as the seed. **Do:** Derive the UUID with the store in which you will use it. *(spec `spec/openapi.yaml`; `createCustomerId.2`)*
