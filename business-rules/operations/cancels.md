# Cancels

## `GET /stores/{storeId}/charges/{chargeId}/cancels` (`listCancels`)

- **silent**, -/lists: The cancels of a charge are listed shortly after a change → The list is not strictly real-time and may lag behind the latest state. **Do:** Use GET on a single cancel, not the list, to read its current status. *(docs `content/ja/docs/api/cancels/request/list.md`; `listCancels.1`)*

## `POST /stores/{storeId}/charges/{chargeId}/cancels` (`createCancel`)

- **loud**, state/errors: A card charge that is awaiting 3-D Secure is canceled → 400 "CANCEL_NOT_ALLOWED". **Do:** Do not cancel a card charge waiting for 3-D Secure; let it complete or fail. **Conflict:** The cancel overview says charges in awaiting or authorized status can be canceled; the tested page shows a card charge awaiting 3-D Secure is refused with CANCEL_NOT_ALLOWED; the record follows the tested page. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/cancels/overview.md`; `createCancel.5`)*
- **loud**, state/errors: A cancel is created for a charge whose payment method does not support cancel or whose status cannot be canceled (for example a paid konbini or bank-transfer charge, or a successful charge, which needs a refund) → 400 "CANCEL_NOT_ALLOWED". **Do:** Check the charge's status and payment method before canceling: cancel only authorized or unpaid charges, and create a refund for a successful card charge instead. *(docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/cancels/overview.md`; docs `content/tested/sandbox-api-behaviour.md`; `createCancel.6`)*
- **loud**, state/-: From 2026-10-05, the 1-yen authorization made by CVV authorization is canceled → outcome not stated. **Do:** Do not try to cancel the 1-yen CVV authorization charge. *(announcement `content/ja/docs/changelog/2026-2.md`; `createCancel.7`)*
- **loud**, state/errors: A cancel is created for a card charge that is already canceled (tested: a canceled authorization) → 400 "CANCEL_NOT_ALLOWED". **Do:** Check the charge status before canceling, and treat 400 CANCEL_NOT_ALLOWED on a charge that GET shows as canceled as already done. **Conflict:** The error table and the definition list payment error 345 (payment already canceled); the tested page shows the cancel request itself is refused at once with 400 CANCEL_NOT_ALLOWED; the record follows the tested page. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; `createCancel.10`)*
- **loud**, idempotency/errors: A cancel is sent again with the same Idempotency-Key after the charge became canceled (cancel does not apply the key) → 400 "CANCEL_NOT_ALLOWED" No Idempotency-Status header is returned. **Do:** Do not rely on an Idempotency-Key to make a cancel retry safe: on CANCEL_NOT_ALLOWED or a timeout re-read the charge with GET to see whether it is already canceled. **Conflict:** The idempotency page says a repeated request with the same key returns the stored response; the tested page shows cancel ignores the key; the record follows the tested page. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/general/idempotent-requests.md`; `createCancel.14`)*
- **loud**, state/errors: A Pay-easy konbini charge that is awaiting (not yet paid) is canceled (tested; an awaiting 7-Eleven konbini charge was canceled with 201) → 400 "CANCEL_NOT_ALLOWED". **Do:** Expect 400 CANCEL_NOT_ALLOWED when canceling an unpaid Pay-easy konbini charge, and do not offer that cancel to the customer. **Conflict:** The cancel overview says awaiting charges can be canceled; the tested page shows an awaiting Pay-easy charge is refused with CANCEL_NOT_ALLOWED; the record follows the tested page. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/cancels/overview.md`; `createCancel.15`)*
- **silent**, account-config/side-effects: `subscription_configuration.suspend_on_cancel` is on and the latest charge of a subscription is cancelled → The subscription is suspended. **Do:** After cancelling a subscription's latest charge, check the subscription and unsuspend it if billing should continue. *(spec `spec/openapi.yaml`; `createCancel.1`)*
- **silent**, account-config/side-effects: The merchant cancels an authorization, or a bank-transfer or konbini application, and the matching email notification is enabled → UnivaPay emails the cancellation notice. **Do:** Do not send a duplicate email for this event unless the matching notification is switched off in the console (General settings > Notifications). *(docs `content/ja/docs/guide/detail/mail/template.md`; docs `content/ja/docs/faq/individual/mail.md`; `createCancel.2`)*
- **silent**, state/side-effects: An authorized card charge is canceled → 201 The cancel is created with status pending and the charge then becomes canceled (the authorization hold is released). **Do:** Poll the cancel or the charge until the charge is canceled. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/cancels/overview.md`; docs `content/ja/docs/guide/first/notification_and_retrieval.md`; `createCancel.3`)*
- **silent**, state/side-effects: A konbini charge that is awaiting (not yet paid) is canceled (tested, including a 7-Eleven charge; an awaiting Pay-easy charge is refused with CANCEL_NOT_ALLOWED) → 201 The charge then becomes canceled, and the konbini cancellation email is sent. **Do:** Cancel unpaid konbini charges when the order is withdrawn. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/cancels/request/create.md`; docs `content/ja/docs/guide/individual/cvs/feature.md`; `createCancel.4`)*
- **silent**, -/webhooks: A charge is canceled → The cancel_finished webhook is sent. **Do:** Subscribe to cancel_finished to learn the cancel result. *(docs `content/tested/sandbox-api-behaviour.md`; `createCancel.8`)*
- **silent**, -/values: In test mode, a card charge made with a number ending in 1881, or a konbini charge with a phone number ending in 1881, is canceled → The charge succeeds but the cancel fails. **Do:** Use these test values to exercise a failed cancel. *(docs `content/ja/docs/api/charges/overview.md`; docs `content/ja/docs/guide/individual/cvs/feature.md`; `createCancel.9`)*
- **silent**, state/side-effects: A cancel is made while the (bank-transfer) account balance is not zero → The cancel fails with payment error 348 (the account balance is not zero, so the cancel cannot continue). **Do:** Do not cancel a bank-transfer charge that has received deposits; settle the deposit with the consumer instead. *(docs `content/ja/docs/api/error/overview.md`; `createCancel.11`)*
- **silent**, -/values: A cancel is created through the API → The cancel reason is null; only cancels created by the platform get a reason (expired when an authorization was not captured in time, or customer_request). **Do:** Treat reason expired as an automatic cancel of an uncaptured authorization. *(spec `spec/openapi.yaml`; `createCancel.12`)*
- **silent**, state/side-effects: A cancel is made on a charge that cannot be canceled (the sources do not say which charges) → The cancel fails with payment error 312 (this charge cannot be canceled). **Do:** Check the cancel until it is final, and on payment error 312 treat the charge as not canceled. *(docs `content/ja/docs/api/error/overview.md`; spec `spec/openapi.yaml`; `createCancel.13`)*
- **silent**, state/side-effects: A bank-transfer or PayPay online charge that is awaiting (not yet paid) is canceled (tested) → 201 The charge then becomes canceled. **Do:** Cancel an unpaid bank-transfer or PayPay request when the order is withdrawn, then confirm the canceled status with GET. *(docs `content/tested/sandbox-api-behaviour.md`; docs `content/ja/docs/api/cancels/overview.md`; `createCancel.16`)*
- **silent**, state/values: A refund or a cancel is requested → Its status changes in stages: `pending`, then `successful`, `failed` or `error`. **Do:** Do not treat the create response as the result; poll the refund or cancel (or wait for its webhook) until it is final. Also: `createRefund`. *(docs `content/ja/docs/guide/first/notification_and_retrieval.md`; docs `content/ja/docs/api/refunds/overview.md`; spec `spec/openapi.yaml`; `createRefund.3`)*

## `GET /stores/{storeId}/charges/{chargeId}/cancels/{id}` (`getCancel`)

- **loud**, auth/-: A cancel is fetched or updated with an application token without its secret → outcome not stated. **Do:** Call GET and PATCH on cancels from the backend with {secret}.{jwt}. Also: `updateCancel`. *(spec `spec/openapi.yaml`; `getCancel.2`)*
- **loud**, resilience/errors: A GET of a payment resource returns 502, 503 or 504 (possibly a temporary network problem) → outcome not stated. **Do:** Retry the GET after a few seconds and do not treat these statuses as a failed payment. Also: `getCharge`, `getRefund`, `getSubscription`. *(docs `content/ja/docs/api/general/polling.md`; `getCharge.3`)*
- **silent**, -/values: A cancel is fetched with polling=true → The server holds the request until the cancel status changes or the polling timeout passes (final statuses: successful, failed, error). **Do:** Repeat GET with polling=true until the cancel is final. *(spec `spec/openapi.yaml`; docs `content/ja/docs/api/general/polling.md`; `getCancel.1`)*
- **silent**, -/values: A charge, refund, cancel or subscription is fetched with `polling=true` → The API polls internally and answers as soon as the resource reaches a final status (charge: canceled, error, failed, successful; refund and cancel: error, failed, successful), or after 3 seconds with whatever status it has then. **Do:** Use `polling=true` instead of a tight client-side loop, and repeat the call if the status is still not final after it returns. Also: `getCharge`, `getRefund`, `getSubscription`. *(docs `content/ja/docs/api/general/polling.md`; spec `spec/openapi.yaml`; docs `content/ja/docs/api/charges/overview.md`; `getCharge.1`)*
